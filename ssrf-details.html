Server-Side Request Forgery (SSRF) Audit

Server-Side Request Forgery (SSRF) occurs when a web application fetches a remote resource without validating the user-supplied URL. Attackers can abuse this to force the web server to read or send data to internal, restricted resources.

1. Types of SSRF Attacks We Test For

A. In-Band / Basic SSRF

The attacker sends requests to internal services and receives the server response directly back on the screen.

  • Internal Port Scanning: Mapping localhost services (`http://127.0.0.1:8080`, `http://localhost:6379`).
  • Internal Service Access: Accessing admin panels or databases blocked by external firewalls.

B. Cloud Instance Metadata Exfiltration

Targeting cloud metadata services to extract sensitive IAM keys and access tokens.

  • AWS / GCP / Azure Metadata Extraction: Querying endpoints like `http://169.254.169.254/latest/meta-data/` to dump cloud access credentials.

C. Blind SSRF

The application triggers remote requests but does not return response data on screen.

  • Out-of-Band (OAST) Monitoring: Using Collaborator servers to detect hidden HTTP/DNS interactions triggered by backend requests.

2. Mitigation & Prevention Rules

  • Allow-List Remote Resources: Restrict outgoing HTTP requests strictly to pre-approved domains and protocols.
  • Block Loopback & Local Addresses: Reject requests directed to `127.0.0.1`, `localhost`, `10.0.0.0/8`, `192.168.0.0/16`, and `169.254.169.254`.
  • Disable Unused URL Schemes: Allow only `http` and `https` protocols; disable `file://`, `gopher://`, `dict://`, and `ftp://`.
  • IMDSv2 Enforcement: Upgrade cloud infrastructure to require session tokens for metadata service queries.

3. Audit Tools & Methodology

We utilize Burp Collaborator, SSRFmap, Interactsh, and custom payload bypass techniques (IP encoding, DNS rebinding) to ensure thorough coverage.
